# Pipeline 验证策略说明

## 核心思路

`verify_pipeline.py` 脚本的目的是：**验证代码逻辑是否正确，而不是验证模型能否被压缩。**

---

## 两种模式对比

### `--light` 模式（本地轻量验证）

```bash
python scripts/verify_pipeline.py --all --light --device cuda
```

**使用场景**：本地开发时，快速验证代码逻辑

**验证内容**：
- ✅ 剪枝代码能不能正确地移除权重？
- ✅ 量化代码能不能正确地转换精度？
- ✅ 蒸馏代码能不能正确地计算损失和回传梯度？
- ✅ 模型保存/加载的格式对不对？
- ✅ 各个函数的输入输出形状匹配不匹配？

**Mock 模型**：一个只有 159K 参数的小型卷积网络，仅作为"替身演员"测试代码流程。

---

### 无 `--light` 模式（服务器完整验证）

```bash
python scripts/verify_pipeline.py --all --device cuda
```

**使用场景**：服务器上，验证真实 DUSt3R 模型

**验证内容**：
- ✅ 真实 DUSt3R 模型（571M 参数）能不能被正确处理
- ✅ 剪枝后模型结构是否正确
- ✅ 量化后能否正常推理
- ✅ 蒸馏损失计算是否正确

---

## 类比解释

| 阶段 | 汽车生产线类比 | 我们的情况 |
|------|---------------|-----------|
| **设计测试** | 用纸板箱模拟汽车，测试生产线流程 | 用 Mock 模型测试 PQK 代码逻辑 |
| **正式生产** | 真正的汽车零件上线 | 用真实 DUSt3R 模型运行实验 |

---

## 为什么需要两种模式？

| 环境 | 本地电脑 (6GB VRAM) | 服务器 (24GB+ VRAM) |
|------|-------------------|-------------------|
| 能加载 DUSt3R？ | ❌ 内存不够 | ✅ 可以 |
| 能跑代码逻辑测试？ | ✅ 用 Mock 模型 | ✅ 用真实模型 |
| 发现代码 bug？ | ✅ 可以 | ✅ 可以 |
| 测量真实压缩效果？ | ❌ 不行 | ✅ 可以 |

**好处**：
- 本地改代码时，可以快速验证"代码写对了没有"
- 不用每次都租服务器来测试代码
- 等代码逻辑确认没问题了，再上服务器跑真实实验
- **节省时间和成本**

---

## 一句话总结

> **`--light` 模式 = 用假数据测真代码**
> 
> Mock 模型只是个"替身演员"，验证的是剪枝/量化/蒸馏代码逻辑是否正确，
> 而不是验证 DUSt3R 能不能被压缩或压缩效果如何。

## 推荐工作流

```
┌─────────────────────────────────────────────────────────────┐
│                    本地电脑                                  │
├─────────────────────────────────────────────────────────────┤
│  1. 编写/修改 PQK 脚本                                      │
│  2. python scripts/verify_pipeline.py --all --light         │
│     └─ 快速验证代码逻辑（几秒钟）                           │
│  3. 通过 → git push                                         │
│  4. 失败 → 修复代码 → 重复步骤 2                            │
└─────────────────────────────────────────────────────────────┘
                              ↓
┌─────────────────────────────────────────────────────────────┐
│                 服务器                                       │
├─────────────────────────────────────────────────────────────┤
│  1. git pull 拉取最新代码                                   │
│  2. python scripts/verify_pipeline.py --all                 │
│     └─ 用真实 DUSt3R 验证（确保一切正常）                   │
│  3. 运行完整 PQK 实验，收集结果                             │
└─────────────────────────────────────────────────────────────┘
```

## Mock 模型结构

```python
class MockModel(torch.nn.Module):
    def __init__(self):
        super().__init__()
        # 使用卷积层，参数量小
        self.encoder = nn.Sequential(
            nn.Conv2d(3, 64, 3, padding=1),
            nn.ReLU(),
            nn.Conv2d(64, 128, 3, padding=1),
            nn.ReLU(),
        )
        self.decoder = nn.Sequential(
            nn.Conv2d(128, 64, 3, padding=1),
            nn.ReLU(),
            nn.Conv2d(64, 3, 3, padding=1),
        )
        # Linear 层用于测试剪枝
        self.fc = nn.Linear(128, 64)
```

- **参数量**：约 159K（vs DUSt3R 的 571M）
- **内存占用**：< 1MB（vs DUSt3R 的 2.7GB）
- **用途**：仅测试代码逻辑，不代表真实性能

## 常见问题

### Q: Mock 模型测试通过，就说明 DUSt3R 也能被压缩吗？

**A: 不是。** Mock 测试只验证代码逻辑正确性。DUSt3R 的实际压缩效果（精度损失、速度提升）需要在服务器上用真实模型测试。

### Q: 为什么不直接在本地测试 DUSt3R？

**A:** DUSt3R 有 571M 参数，需要约 2.7GB 显存。本地 RTX 3060 (6GB) 可以勉强推理，但做剪枝/量化/蒸馏时内存会翻倍，容易 OOM。

### Q: 什么时候需要上服务器？

**A:** 当你需要：
1. 测量真实的压缩效果（精度、速度、模型大小）
2. 运行完整的训练流程（蒸馏需要大量 GPU 内存）
3. 在标准数据集上评测
